# Sprint 4.6 — Error Contract Completeness

## Goal

- Close the gap between the documented Phase 4 machine contract and the
  runtime error surface for aggregate install failures and backend error
  metadata.

## Hard Dependencies

- Sprint `4.5` complete.

- `src/pkg/api/errors.go`

## Required Work

- Preserve typed error categories in aggregate (multi-scope) install failure
  envelopes. When all-scopes-failed or partial multi-scope failure occurs,
  propagate the most specific per-scope typed code (`blocked`,
  `confirmation_required`, `invalid_args`, backend failure codes) rather than
  collapsing to `internal_error`. Per-scope structured sub-errors must be
  present in `failures[]`.
- Populate `retryable`, `suggested_action`, `cause_code`, and `operation` in
  runtime error responses where the Phase 4 contract defines them. Backend
  failures, transient network errors, and confirmation-required states must set
  `retryable` and `suggested_action` where those fields are meaningful.
- Ensure no regression: all existing typed error paths (pre-multi-scope
  single-scope failures) must continue to emit correct codes.

## Implementation Notes

`install.go:177-192` (all-scopes-failed path) and `install.go:231-249`
(partial multi-scope path) both hardcode `api.ErrorCodeInternal`. These must
inspect the per-scope failure reasons and surface the dominant or most specific
typed code instead.

`json_errors.go:50-66` writes only `code/message/details`.
`json_errors.go:116-128` only injects `details.client`. Add runtime population
of `retryable`, `suggested_action`, `cause_code`, and `operation` for backend
failure, transient, and confirmation-required paths.

`contract.go:19-24` already defines `Retryable`, `Details`, and
`SuggestedAction` — wire them at the error construction sites.

## Acceptance Criteria

- All-scopes-failed aggregate install returns the typed code of the dominant
  per-scope failure, not `internal_error`.
- Partial multi-scope failure envelope carries per-scope structured sub-errors
  with typed codes.
- `retryable` is `true` for transient backend failures and `false` for
  deterministic failures (invalid args, local-modification blocks).
- `suggested_action` is populated for `confirmation_required` and recoverable
  backend errors.
- `cause_code` and `operation` are populated for backend failure envelopes.
- Existing single-scope typed error codes are unchanged (no regressions).
- Contract tests cover: all-scopes-failed with typed sub-errors,
  partial-failure with mixed typed sub-errors, backend failure with retryable
  metadata, confirmation-required with suggested_action.
