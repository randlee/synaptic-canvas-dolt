# Sprint 5.4 — DoltHub Smoke Test

## Goal

- Prove the same imported package works against the live DoltHub-backed catalog.
- Confirm the remote-backed user experience matches the local-clone proof closely enough for MVP release confidence.
- Record any backend differences explicitly so they are not discovered for the first time during release.

## Hard Dependencies

- Sprint 5.3 completed the local-clone proof for the same package.
- The imported package is available on a DoltHub-backed test catalog branch.
- Credentials and configuration required for the DoltHub-backed read path are available in the test environment.

## Exact Targets

- DoltHub-backed test catalog containing the imported package
- Test repository for local-scope install
- Machine-global install target on the test workstation
- Evidence log comparing local-clone and DoltHub behavior

## Required Work

- Upload or promote the imported package to the DoltHub-backed test catalog branch used for live smoke testing.
- Verify `list` and `info` resolve the package from the remote catalog before install testing begins.
- Run `install`, `status`, `validate`, `upgrade`, `uninstall`, and reinstall flows against the DoltHub-backed path through the public `sc` CLI with `--json`.
- Exercise both project-local scope and machine-global scope installs using the remote-backed catalog.
- Compare the live DoltHub behavior with the local-clone proof and record any differences in output, error typing, or package availability.

## Implementation Notes

- This is a live human/AI-driven smoke test, not a CI gate. Treat it as release evidence, not as a flaky network-dependent automation job.
- Keep the package/version/branch under test aligned with the local-clone pass so comparison remains meaningful.
- Do not bypass the public CLI contract with direct remote SQL or hand-edited install state during smoke validation.
- If a backend-specific difference is expected, write it down. Do not leave it implied.

## Non-Goals

- Do not replace the local-clone proof with DoltHub-only evidence.
- Do not start a broad package matrix before the first package passes both local-clone and DoltHub smoke tests.
- Do not normalize away remote-specific failures in the report.

## Acceptance Criteria

- The imported package can be discovered and installed from the DoltHub-backed catalog.
- Local-scope install, global-scope install, `status`, `validate`, `upgrade`, `uninstall`, and reinstall flows pass against the remote-backed path.
- The local-clone and DoltHub passes can be compared package-for-package and branch-for-branch.
- Any backend-specific difference is written down explicitly with follow-up action if needed.

## Required Validation

- `(cd src && go test ./...)`
- `(cd src && go test ./... -race)`
- `(cd src && golangci-lint run ./...)`
- `git diff --check`

## Completion Report Requirements

- Record any DoltHub-specific issues encountered and the exact fixes completed during Sprint 5.4.
- Record any remote-versus-local behavior differences, even when they are resolved in the same sprint.
- Record any unresolved DoltHub or live-environment blockers as explicit follow-up items for later sprints.
