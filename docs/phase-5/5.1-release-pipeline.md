# Sprint 5.1 — Release Pipeline

## Goal

- Define and implement an MVP release pipeline that is explicit about the supported archive matrix and validates GoReleaser configuration before tags are cut.
- Keep MVP release scope unambiguous by documenting Homebrew prerequisites and the enabled Winget publication path's remaining operational requirements while preserving tag-triggered publication for the shipped release surface.

## Hard Dependencies

- Phase 4 merged into `develop` and `integrate/phase-5` is current with that baseline.
- GoReleaser is available in CI and in maintainer environments used for non-publishing dry runs.
- Homebrew tap access for `randlee/homebrew-tap` is provisioned before the first tagged publish.
- PR #55 baseline is already merged into `develop`, so Sprint 5.1 starts from a release configuration where the Winget publish path is enabled in `.goreleaser.yml`.

## Required Work

- Create a non-publishing release-validation workflow (`.github/workflows/release-validate.yml`) on pull requests and pushes that runs `goreleaser check` against the repository release config; keep the tagged publish workflow focused on actual release publication.
- Update `.github/workflows/release.yml` to document or implement non-blocking behavior for Homebrew tap update failures so GitHub release artifacts still publish if the tap update fails.
- Update `.goreleaser.yml`, `docs/synaptic-canvas-cli.md`, and `docs/project-plan.md` so they match current MVP release scope: Homebrew and release archives active, `go install` available, `windows/arm64` included as a secondary archive target, Winget publication path enabled in config, and `release-validate.yml` added by Sprint 5.1.
- Update `docs/project-plan.md` Phase 5 summary so it references this sprint plan, names the explicit release matrix, and reflects the dry-run validation and Homebrew prerequisite/failure policy.

## Implementation Notes

- `amd64` is the Go/GoReleaser architecture name for x64/x86_64. Use both the Go names and the human-readable platform labels so reviewers do not confuse `amd64` with a legacy-only target.
- **Release matrix:** Primary: `darwin/arm64`, `windows/amd64`, `linux/amd64`. Secondary: `darwin/amd64`, `windows/arm64`, `linux/arm64`.
- **Winget:** The publish path is already enabled in `.goreleaser.yml`. Sprint 5.1 must document the remaining operational prerequisites clearly: publisher registration/review path, `WINGET_GITHUB_TOKEN`, and the fact that enablement in config does not guarantee catalog availability.
- Preferred CI shape: leave `.github/workflows/release.yml` tag-triggered for publishing, and add `.github/workflows/release-validate.yml` for PR/push validation running `goreleaser check`.
- Homebrew publication requires `HOMEBREW_TAP_TOKEN` with at least `contents:write` on `randlee/homebrew-tap`. Treat tap update failures as a warning path that does not block the GitHub release artifact outcome.

## Non-Goals

- Do not broaden MVP scope beyond the documented release archive matrix and existing installer/runtime boundaries.
- Do not move ATM orchestration, team workflow policy, or package-management business logic into release scripts or `sc:plugin`.

## Acceptance Criteria

- A detailed Sprint 5.1 plan exists in `docs/phase-5/5.1-release-pipeline.md` and the Phase 5 summary in `docs/project-plan.md` points to it.
- `.github/workflows/release-validate.yml` exists and runs `goreleaser check` on PR/push without requiring a tag; tagged publish workflow remains the only publishing path.
- `.goreleaser.yml`, `docs/synaptic-canvas-cli.md`, and `docs/project-plan.md` all state the same MVP release surface: primary `darwin/arm64`, `windows/amd64`, `linux/amd64`; secondary `darwin/amd64`, `windows/arm64`, `linux/arm64`; Winget publication path enabled in config with remaining operational prerequisites documented explicitly.
- `docs/synaptic-canvas-cli.md` states that `release-validate.yml` is Sprint 5.1 work rather than historical baseline behavior.
- Sprint documentation specifies `HOMEBREW_TAP_TOKEN`, `WINGET_GITHUB_TOKEN`, the required `contents:write` permission on `randlee/homebrew-tap`, and the non-blocking behavior when tap update fails.
- `git diff --check` passes for the release-planning changes.
